Product Experience

用户真正需要的，是三种不中断学习的能力

01

翻译字幕与克隆配音

原视频立即播放；字幕、翻译和声音克隆按时间 Cue 逐步可用，而不是等待整段导出。

02

框选画面，直接追问

选中画面区域后，AI 同时看到源分辨率截帧、当前时间点和邻近字幕上下文。

03

快速获得视频摘要

复用转写缓存与少量代表帧，优先产出可读摘要，再由用户决定是否保存为资料。

三项能力共用当前 Asset、媒体 Anchor、Provider Selector 与稳定会话；差异只在 Workbench 提供的上下文。

Experience Principle

第一原则：播放永远先于 AI

打开媒体时同时启动三条车道。任何后台能力缺失、失败或被取消，都不能让用户失去原始播放。

Localization Flow

字幕先到，翻译和配音逐 Cue 跟上

STEP 01

Decode + VAD

抽取统一时间基的 PCM，按语音边界形成稳定片段。

STEP 02

原文 ASR Cue

先显示原文；每个 Cue 有稳定 ID、起止时间和修订状态。

STEP 03

小批字幕翻译

携带邻近 Cue 保持术语一致，失败时不影响原文轨。

STEP 04

Voice Profile

用用户确认的短人声片段建立可追溯声音配置。

STEP 05

Cue TTS + 热替换

单条翻译就绪即合成；播放器收到 cue.audio-ready 后试听。

原文轨始终保留翻译轨可独立失败配音 Cue 可单条重试最终导出不阻塞预览

Separation Strategy

人声分离是后台缓存，不是播放前置条件

后台
可抢占
可缓存

首轮可用 htdemucs · shifts=1 做交互基线，但 Demucs 官方仓库已经归档，因此必须同时 benchmark 维护中的替代方案，不能直接定为长期默认。

01
当前播放附近 Cue字幕与配音最先抢到计算资源。
02
用户选中的 3–10 秒片段快速准备音色预览，不等待全视频。
03
完整 vocals / accompaniment低优先级生成并缓存为版本化 Artifact。
分离不等于说话人识别；多人视频仍需单独设计 diarization 与 voice-profile 绑定。

Conversation Continuity

连续对话靠 Provider Session，不靠 Renderer 重放历史

一次用户请求仍然是一条 GenerationTask；只要解析出相同的 workspace instance key，多个任务就可以恢复同一个 Provider thread。

Turn 01框选对象是什么？
GenerationTask A
Turn 02它为什么这样运动？
GenerationTask B
Turn 03总结成一条笔记。
GenerationTask C
同一个 Provider SessionCodex thread / future Claude session
workspaceKey + instanceKey(conversationId) + providerId
Renderer 消息：用于展示GenerationTask：用于一次请求的状态与恢复Provider Session：上下文事实源
若某项生成需要彻底隔离，只需使用 taskId 作为 instance key；不需要另造第二套会话系统。

Data Lifecycle

缓存、笔记和派生资料必须分层

不是所有 AI 结果都要变成 Asset。先判断它能否重建、是否需要长期学习、是否要参与后续引用。

Artifact

可删除后重建的缓存
  • media.transcript.v1
  • media.stems.v1
  • media.voice-profile.v1
  • media.dub-track.v1

Attachment

附着在 Asset / Anchor 上的记录
  • 某个时间点的 AI 回答
  • 框选区域的解释
  • 用户确认保存的摘要卡片
  • 可跳回媒体位置的学习笔记

Derived Asset

正式进入项目的派生资料
  • 克隆配音后的视频
  • 可编辑 Markdown 摘要
  • 后续讲义或思维导图
  • 可再次被生成任务引用
Derived Asset ── AssetReference / AssetLink ──▶ Source Video / Audio

Acceptance Gates

首版用延迟和稳定性验收，不用模型名验收

先在代表性 Windows CPU / GPU 上采集真实基线，再决定默认模型、量化、并发和是否启用 GPU。

Open → Play首帧与可交互时间
First Cue首次稳定原文字幕
First Translation首次目标语言 Cue
First Audio Packet首次克隆配音可听
Export Complete最终轨道封装完成
RTFASR / 分离 / TTS 各自的实时率
VRAM / RAM并发作业的峰值与 OOM 降级
Cancel / Resume切换 Asset、取消与重启后的恢复
Cache Hit相同 source revision 是否避免重复计算
特别关注 8 GB GPU 下 Whisper、分离与 TTS 的竞争；调度优先用户正在看的 Cue 和选中片段。

Implementation Order

实施顺序：先公共主路，再加重模型

PHASE 01 · EXPERIENCE SPINE

先让问答与上下文走通

  • Workbench Conversation Descriptor / Controller / UI
  • Video frame-region Anchor 与可信截帧
  • Transcript Artifact 与快速摘要 TaskDefinition
  • 取消、失败、无 Provider 配置的完整反馈
PHASE 02 · STREAMING MEDIA AI

再接本地字幕与配音

  • Media Job Scheduler 与领域事件
  • FFmpeg + whisper.cpp 基础包
  • 短片段 Voice Profile 与 Cue TTS
  • 分离候选模型的本机 benchmark
PHASE 03 · PRODUCTIZATION

最后做完整导出与质量档位

  • 全片 stems、字幕轨和配音轨缓存
  • 配音视频 Derived Asset 与 Reference
  • CPU/GPU 质量档位与资源调度
  • Audio Workbench 复用同一能力主路
